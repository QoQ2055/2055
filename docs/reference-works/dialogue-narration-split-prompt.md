## 一、JSON Schema（修正版）

> ⚠ 原文中的示例 JSON 格式错乱（引号嵌套混乱、字段错位、不可解析）。本档采用**修正后的清晰 schema**：

### 1.1 单条记录 TypeScript Interface

```ts
type Emotion = '高兴' | '生气' | '伤心' | '害怕' | '厌恶' | '低落' | '惊喜' | '平静';
type Strength = '微弱' | '稍弱' | '中等' | '较强' | '强烈';

interface DialogueUnit {
  role_name: string;       // 角色名 或 "旁白"
  text_content: string;    // 拆分后的文本片段（35-50 字含标点）
  emotion_name: Emotion;   // 情绪
  strength_name: Strength; // 强度
}

type ChapterScript = DialogueUnit[];
```

## 二、核心规则总结

### 2.1 台词识别

| 规则 | 说明 |
|---|---|
| 标记符号 | 中英双引号 `""` `""`、破折号 `——`、感叹号 `!`、冒号 `:` 后的引语 |
| 双引号统一化 | 双引号 `""` → 单引号 `''`（保留为 text_content 内嵌字符） |
| 角色匹配 | 优先用 `possible_characters` 列表中的角色名；不在列表则上下文推断 |
| 长度上限 | 单条 ≤ 50 字（含标点） |
| 长度下限 | 35-50 字为提取窗口（保证语义完整前提下） |
| 合并策略 | 同角色相邻台词可合并，但不超 50 字 |
| 完整性 | 必须 100% 保留原文，不得删改或省略 |

### 2.2 旁白识别

非台词的全部叙述内容（心理活动 / 环境描写 / 动作描写 / 场景过渡）→ `role_name = "旁白"`。

规则同台词（35-50 字 / 不删改 / 不超 50 字）。

### 2.3 情绪与强度标注

- 严格从 `possible_emotions` 与 `possible_strengths` 枚举中选取
- **旁白统一**：`emotion_name = "平静"`, `strength_name = "中等"`
- 情绪仅作标注，**不得改写原文**

### 2.4 预定义枚举

- **可能角色（运行时由用户提供）**：示例为 `程平安的婆婆 / 旁白 / 周报琴 / 程平安 / 村长 / 信`
- **情绪 8 项**：`高兴 / 生气 / 伤心 / 害怕 / 厌恶 / 低落 / 惊喜 / 平静`
- **强度 5 项**：`微弱 / 稍弱 / 中等 / 较强 / 强烈`

## 三、原文（保真）

```
你的任务是将给定小说内容划分为角色和内容，并输出为结构化 JSON 结果。

台词识别规则:
1. 必须完整保留原文内容，不得遗漏、删改或省略任何字句。
2. 提取角色对话内容和旁白。识别所有内容，包括带引号("")如果是双引号的内容，
   提取出来之后将双引号改成''、破折号(--)、感叹号(!)、冒号(:)等常见台词标记的文本，
   其余均为旁白内容。
3. 若角色在已知角色列表中，则直接使用该角色名；若不在列表中，则根据上下文合理判断角色身份。
4. 相邻台词如属同一角色，可合并为一条，但单条台词长度不得超过 50 字（标点符号也算，
   拆分的文案放在 "text_content" 中）。
5. 若单条台词超过 50 字，需按语义完整性拆分为多条，每条不超过 50 字（标点符号也算），
   拆分的文案放在 "text_content" 中，并确保原文内容不缺失。
6. 在保证单句话完整性的基础上，以 35-50 字（标点符号也算）为一个对话提取限制。
7. 确保原文没有漏，不会出现原文截断。
8. 如果是拆分的对话，要保证是同一角色说的。

旁白识别规则:
1. 所有非台词的叙述性内容（包括心理活动、环境描写、动作描写、场景过渡等）均标记为"旁白"。
2. 必须保留原文的所有文字内容，不得遗漏、删改或省略任何字句。
3. 相邻的旁白内容可合并为一条，但单条长度不得超过 50 字（标点符号也算）。
4. 若单条旁白超过 50 字，需按语义完整性拆分为多条。
5. 在保证单句话完整性的基础上，以 35-50 字为一个提取限制。
6. 如果是拆分的对话，要保证是同一角色说的。
7. 确保原文没有漏，不会出现原文截断。

情绪与情绪强度识别规则:
1. 根据上下文语境、语气及场景变化，为每条台词识别情绪和情绪强度。
2. 情绪与强度必须严格从提供的 possible_emotions 与 possible_strengths 中选择。
3. "旁白"内容的情绪与强度统一为：情绪"平静"，强度"中等"。
4. 情绪识别不得影响或改写原文内容，仅用于标注。

特殊情况处理:
1. 角色连续对话时，确保每条台词对应正确角色，避免角色错配。
2. 当段落中混合出现旁白与台词时，应拆分为独立记录：旁白一条、台词一条。
3. 输出结果不得出现遗漏、重复、合并错误或原文缺失的情况。
4. 拆分、合并及情绪标注仅为结构化目的，须保证原文内容 100% 完整保留。

输出格式: 严格输出为 JSON 数组。

输入变量:
- possible_characters: 角色枚举
- possible_emotions: 情绪枚举（高兴/生气/伤心/害怕/厌恶/低落/惊喜/平静）
- possible_strengths: 强度枚举（微弱/稍弱/中等/较强/强烈）
```

## 五、未来"有声书导出"功能的开发蓝图（草案）

### 5.1 数据结构

实现 `DialogueUnit` interface（参见第一节）+ Dexie 表存储拆分后的章节脚本。

### 5.2 章节 → 配音脚本的 LLM 转换

新建独立功能（**不**作为 craft 层方法模块，避免污染创作流程）：
- 输入：章节正文 + 项目角色列表
- 输出：`DialogueUnit[]`
- 调用 LLM：本档 prompt + `response_format: { type: "json_object" }`（参见 `@docs/internal-notes/deepseek-v4-tuning-guide.md` 五）
- 推荐模型：V4 Flash（格式化提取任务，温度 0.3，禁用 thinking）

### 5.3 输出适配

- 多 TTS 平台适配器（豆包 TTS / Azure TTS / ElevenLabs / 阿里云语音 / ...）
- 角色 → 音色映射（用户配置 `roleVoiceMap: Record<string, VoiceId>`）
- 情绪 → SSML / TTS 参数映射（pitch / rate / volume / style）

### 5.4 注入节点

新建 `novel.5`（音频导出层），与 `novel.4`（视频/分镜导出层）平级，**与小说创作主流程 `novel.1-3` 解耦**。

### 5.5 UI

- 章节脚本表格视图（行 = DialogueUnit，列 = 角色/文本/情绪/强度）
- 行级编辑（修正 LLM 拆错的角色或情绪）
- 一键导出 SSML / 一键调用 TTS API 合成音频
