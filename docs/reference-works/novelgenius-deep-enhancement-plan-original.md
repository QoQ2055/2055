# NovelGenius AI Studio 系统性功能增强深度方案

> 版本：2.0 | 日期：2026-04-25 | 基于 DeepSeek V4 技术报告、社区实测、API 对比实验

---

## 第一章 现状诊断：我们到底出了什么问题

### 1.1 问题全景

NovelGenius 当前的大纲生成管线由五个核心场景组成。通过逐行代码审阅和 API 实测，每个场景都存在不同层次的问题。以下是完整的问题矩阵：

| 场景 | 当前实现 | 核心问题 | 问题根因 | 严重程度 |
|------|---------|---------|---------|---------|
| 卷纲参考解析 | 单步提取，temp=0.3 | 输出与参考文本几乎一模一样 | Prompt 定位为"提取"而非"创作"；缺乏项目上下文注入 | 致命 |
| 自动卷纲生成 | 单步生成，temp=0.7 | 卷纲内容空泛，缺乏叙事深度 | Prompt 只要求标题+章数+节奏，没有要求核心冲突/悬念/角色弧 | 严重 |
| 简要大纲推演 | 批量生成，temp=0.7 | 章节间缺乏因果链和伏笔呼应 | 批次间上下文断裂；卷纲信息注入方式为简单文本拼接 | 严重 |
| 大纲增强 | 四层记忆+钩子链，temp=0.7 | 增强后内容与简要大纲高度重复 | 四层记忆虽有但 Prompt 中没有明确要求"在简要基础上新增什么" | 中等 |
| 章节正文生成 | WRITER agent，useThinking=true（死代码） | Thinking Mode 从未生效；ANTI_AI_DETECTION_RULES 过长且与 system prompt 矛盾 | useThinking 参数未传入 API 调用；V4 Thinking Mode 下 temperature 无效 | 严重 |

### 1.2 API 实测验证：卷纲参考解析的"复制"问题

我们用相同的测试用例（参考文本：修仙小说五卷结构；目标项目：《星辰武神》武道故事）进行了三组对比实验：

**实验一：现有 Prompt，temperature=0.3**

参考文本关键词（林风、玉佩、青云、魔修、秘境、邪神、天玄门、苏瑶、张浩、飞升）命中率 **10/10**。目标项目关键词（叶辰、苏灵儿、萧战、星辰、武神、武院、王朝、域外）命中率 **0/8**。结论：完全复制。

**实验二：现有 Prompt，temperature 提升至 0.7**

参考文本关键词命中率仍然 **10/10**，目标项目关键词命中率仍然 **0/8**。结论：提高 temperature 无法解决问题，因为 Prompt 结构本身就是提取任务。更关键的是，**DeepSeek V4 开启 Thinking Mode 后 temperature 参数完全失效**，这意味着试图通过调参来控制创造力在 V4 上是一条死路。

**实验三：两阶段法（先解构结构，再融合重构）**

阶段一输出纯抽象结构模式（卷数比例、转折点位置、情感波形），无任何具体角色名/地名。阶段二注入完整项目上下文后重构，参考文本关键词命中率 **0/10**，目标项目关键词命中率 **8/8**。结论：两阶段法彻底消除了内容复制。

### 1.3 底层代码中的隐蔽缺陷

**缺陷一：useThinking 死代码**

`writingService.ts` 中为章节正文生成设置了 `useThinking: true`，但在 `gemini.ts` 的 `generateAgentResponse` 函数中，`ai.chat.completions.create()` 调用完全没有传入任何 thinking 相关参数。DeepSeek V4 API 需要通过 `extra_body: { thinking: { type: "enabled" } }` 来启用 Thinking Mode，但代码中不存在这样的字段。这意味着所有标记了 `useThinking: true` 的场景，Thinking Mode 从未真正生效。

**缺陷二：response_format 未使用**

DeepSeek V4 API 原生支持 `response_format: { type: "json_object" }`，可以强制模型输出合法 JSON。但当前代码中所有结构化输出场景（卷纲、大纲）都只靠 Prompt 中的文字描述来引导 JSON 输出，没有使用 API 级别的 JSON 模式。这导致偶尔出现 JSON 解析失败。

**缺陷三：COMMON_BRAIN_LOGIC 与 ANTI_AI_DETECTION_RULES 的自相矛盾**

`COMMON_BRAIN_LOGIC` 系统提示词教导 AI 使用"神经叙事学"概念（多巴胺、皮质醇、催产素），但 `ANTI_AI_DETECTION_RULES` 又严禁使用这些术语。在 DeepSeek V4 的 Thinking Mode 下，模型会在思维链中使用这些概念进行推理，然后在输出中试图回避，导致输出质量不稳定——模型在"用"和"不用"之间反复纠结。

## 第二章 DeepSeek V4 模型特性深度解析

### 2.1 V4 Flash vs V4 Pro：不是"好与差"，而是"不同的武器"

基于 DeepSeek 官方技术报告（2026-04-24）、社区大规模实测（Reddit SillyTavernAI）和 API 文档的综合分析，两个模型的特性差异可以精确描述如下：

| 维度 | V4 Flash（284B 参数，13B 激活） | V4 Pro（1.6T 参数，49B 激活） |
|------|-------------------------------|------------------------------|
| 指令遵循 | 弱。大量忽略 preset 中的格式/结构指令，忽略角色卡中的关键信息 | 强。很好地遵循格式和结构指令，CoT 能更好地处理复杂约束 |
| 散文质量 | 好。在纯散文评测中得分甚至高于 V3.2 和 V4 Pro | 更好。社区评价为"V3.2 dialed up to 12" |
| 创造力 | 社区反映"dry and nowhere near as creative"，Thinking Mode 下更明显 | 更有创造力，但 reasoning_effort=high 时也会变"干" |
| 输出量 | 大。比 V3.2 多写 45%+（4000-5000 词 vs 2500-3000 词） | 中等。输出量适中 |
| 速度 | 快。比 V4 Pro 快约 3 倍 | 慢 |
| 成本 | 输入 $0.14/M，输出 $0.28/M（缓存命中时输入仅 $0.028/M） | 输入 $1.74/M，输出 $3.48/M（约 Flash 的 12 倍） |
| JSON 输出 | 简单结构可靠，复杂嵌套偶有格式错误 | 复杂结构也能可靠输出 |
| 长上下文 | 1M tokens，MRCR 1M 得分 78.0 | 1M tokens，MRCR 1M 得分 83.5 |
| 中文知识 | Chinese-SimpleQA 78.8 | Chinese-SimpleQA 84.4 |
| 中文创意写作 | 无官方评测数据 | 指令遵循 60.0% 胜率，写作质量 77.5% 胜率（vs Gemini-3.1-Pro） |

### 2.2 Thinking Mode：被忽视的核武器

DeepSeek V4 的 Thinking Mode 是一个被 NovelGenius 完全忽视的关键能力。它的工作机制和限制如下：

**启用方式**：通过 `extra_body: { thinking: { type: "enabled" } }` 传入 API 调用。当前代码中完全没有这个参数。

**关键限制**：开启 Thinking Mode 后，`temperature`、`top_p`、`presence_penalty`、`frequency_penalty` 参数**全部失效**。设置这些参数不会报错但也不会生效。这意味着在 Thinking Mode 下，**控制创造力的唯一途径是 Prompt 工程本身**。

**reasoning_effort 控制**：支持 `"high"`（默认）和 `"max"`（复杂任务自动升级）两个有效档位。`"low"` 和 `"medium"` 会被映射到 `"high"`。

**DeepSeek 官方员工推荐的两种思维模式**（由 DeepSeek 员工 Deli Chen 在 GitHub 发布）：

> **角色沉浸模式**：在第一轮用户消息末尾追加指令，让模型在 `<think>` 标签内以角色第一人称进行内心独白式推理。适用于需要情感深度的创作场景。

> **纯分析模式**：在第一轮用户消息末尾追加指令，让模型在 `<think>` 标签内只进行纯逻辑分析，不使用角色内心独白。适用于需要冷静规划的结构化场景。

**关键技术细节**：这些指令必须放在**第一轮用户消息的末尾**（不是 system prompt），因为这是 V4 训练时使用的注入位置，效果最稳定。当前 NovelGenius 的所有指令都放在 system prompt 中，不是最优注入位置。

### 2.3 社区验证的 Prompt 工程原则

基于 Reddit SillyTavernAI 社区的大规模实测，以下原则已被验证有效：

**原则一："角色沉浸式 Prompt"优于"禁止清单式 Prompt"**

不要说"禁止使用XX词"，而是让模型相信"你（角色）不会这样说话"。这被称为"gaslight 模式"。例如，不要写"严禁使用'不禁'、'竟然'等词"，而应写"你的叙述从不使用对比否定句式。你只描述发生了什么，而非没有发生什么。'你保持警惕'，而非'你没有放松警惕'。"

**原则二：Flash 适合简单交互，Pro 适合重指令场景**

社区共识是"flash for simple back and forth msg, pro for heavy instruction following"。Flash 的问题不是"写不好"而是"不听话"。

**原则三：非推理模式可能更适合散文风格控制**

对于纯创意写作（如章节正文），non-reasoning 模式反而比 reasoning 模式更好地遵循风格指令。reasoning_effort=high 会导致写作"dry"（干燥、缺乏创造力）。

**原则四：V4 的 CoT 会以角色身份推理**

V4 的思维链倾向于以第一人称进行推理，这可以被利用来增强角色一致性和情感深度。

## 第三章 场景化 Prompt 工程详细设计

### 3.1 设计原则

在给出每个场景的完整 Prompt 之前，需要明确以下设计原则：

**原则一：Prompt 结构分层**

每个 Prompt 由三层组成，各层职责明确：

| 层级 | 位置 | 职责 | V4 特性适配 |
|------|------|------|-----------|
| System Prompt | `role: "system"` | 角色身份定义 + 通用写作风格 | V4 对 system prompt 权重高（直接拼接在 BOS 后） |
| User Message 主体 | `role: "user"` 前半段 | 任务描述 + 项目上下文 + 输出格式要求 | 包含具体的创作指令和约束 |
| User Message 尾部注入 | `role: "user"` 末尾 | Thinking Mode 控制指令 | DeepSeek 官方推荐的注入位置，训练时的最优位置 |

**原则二：场景决定模型，模型决定参数**

不同场景对模型能力的需求不同，应该根据场景特性选择模型和参数，而非全局统一设置：

| 场景类型 | 核心需求 | 推荐模型 | Thinking Mode | reasoning_effort |
|---------|---------|---------|--------------|-----------------|
| 结构化规划（卷纲、大纲骨架） | 指令遵循 + 逻辑推理 | V4 Pro | 启用 | high |
| 创意扩展（大纲增强、章节正文） | 创造力 + 情感深度 | V4 Flash 或 V4 Pro | 视场景而定 | — |
| 格式化提取（参考解析、场景拆分） | 准确性 + 格式合规 | V4 Flash | 禁用 | — |
| 风格润色（去AI化） | 风格控制 + 文学性 | V4 Flash | 禁用 | — |

**原则三：禁止清单 → 角色化风格描述**

将当前的 `ANTI_AI_DETECTION_RULES`（约 1500 字的"严禁"列表）重写为角色化的写作风格描述。这不仅更符合 V4 的 Prompt 工程最佳实践，还能减少约 60% 的 token 消耗。

### 3.2 场景一：卷纲参考解析（两阶段法）

**当前问题**：用户粘贴参考卷纲后，AI 输出与参考文本几乎一模一样。

**根因**：单步提取 Prompt + 缺乏项目上下文 + 参考原文直接注入。

**新设计**：两阶段法——先解构结构模式，再融合项目信息重构。

#### 阶段一：结构解构（Structure Deconstruction）

**目的**：从参考文本中提取抽象的叙事结构模式，不包含任何具体内容。

**推荐模型**：V4 Flash，Thinking Mode 禁用（这是一个格式化提取任务）

**推荐参数**：`temperature: 0.4`（Thinking Mode 禁用时 temperature 有效）

**完整 System Prompt**：

```
你是一位叙事结构分析师。你的工作是从小说文本中提取抽象的结构模式——节奏曲线、篇幅比例、转折点位置、情感波形——而不是复述文本内容。你从不引用原文中的角色名、地名、事件名或任何具体情节。你只关注"骨架"，不关注"血肉"。
```

**完整 User Message**：

```
请分析以下参考文本的分卷叙事结构，提取其抽象的结构模式。

【参考文本】
${referenceText.slice(0, 3000)}

【分析要求】
请以纯文本格式输出以下维度的分析结果。注意：你必须只输出抽象的结构模式，严禁出现参考文本中的任何角色名、地名、组织名或具体事件描述。

1. 卷数与篇幅比例
   - 共几卷，每卷占总篇幅的百分比是多少
   - 哪一卷最长，哪一卷最短，为什么

2. 节奏曲线（Pacing Curve）
   - 每一卷的节奏定位（铺垫/上升/高潮/下降/收束）
   - 全书的节奏波形是什么形状（单峰/双峰/阶梯式/螺旋上升）

3. 转折点位置
   - 主要转折点出现在全书的什么百分比位置
   - 每个转折点的功能是什么（如：打破日常、提升赌注、黑暗时刻、最终决战）

4. 卷间衔接模式
   - 每一卷的结尾是如何过渡到下一卷的（悬念钩子/时间跳跃/空间转换/新势力登场）
   - 是否存在跨卷伏笔

5. 情感波形
   - 每一卷的主导情感基调是什么（如：希望/恐惧/愤怒/悲伤/释然）
   - 情感的整体走向是什么（从X到Y）

6. 角色功能分布（不要提及具体角色名）
   - 主角在每一卷中的功能角色是什么（如：学徒/挑战者/领袖/牺牲者）
   - 对手/反派在每一卷中的存在方式是什么（如：暗线/正面冲突/终极对决）
```

**预期输出**：一段纯文本分析，包含卷数比例（如"20%/22%/20%/18%/20%"）、转折点位置（如"20%/42%/62%/80%"）、情感波形等抽象模式，不包含任何具体角色名或事件名。

#### 阶段二：融合重构（Creative Reconstruction）

**目的**：基于阶段一提取的结构模式和当前项目的完整上下文，创作全新的卷纲。

**推荐模型**：V4 Pro，Thinking Mode 启用（这是一个需要深度思考的创作任务）

**推荐参数**：Thinking Mode 启用时 temperature 无效，通过 Prompt 控制创造力

**完整 System Prompt**：

```
你是一位资深的长篇小说策划编辑，拥有二十年的网文和实体出版经验。你擅长根据叙事结构理论为每一部独特的小说设计量身定制的分卷架构。你的卷纲设计总是紧密围绕作品自身的角色、世界观和核心冲突展开，从不套用其他作品的具体情节。
```

**完整 User Message**：

```
我正在创作一部长篇小说，需要你根据以下结构模式和项目信息，为我的小说设计原创的分卷架构。

【参考结构模式】（来自另一部作品的抽象结构分析，仅供参考节奏和比例）
${phaseOneOutput}

【我的小说信息】
- 书名：《${activeProject.title}》
- 故事梗概：${activeProject.synopsis}
- 主要角色：
${activeProject.characters.map(c => `  · ${c.name}：${c.role}，${c.description}`).join('\n')}
- 世界观设定：${activeProject.worldBuilding || '未设定'}
- 目标总章数：${targetChapterCount} 章
- 小说类型/流派：${activeProject.genre || '未指定'}

【设计要求】
请为《${activeProject.title}》设计分卷架构。你必须完全基于上述"我的小说信息"进行原创设计，参考结构模式仅用于借鉴节奏比例和转折点位置，不得借用其中的任何具体情节或角色设定。

每一卷需要包含以下信息：

1. **卷名**：体现本卷核心主题的标题
2. **章数分配**：本卷包含多少章（所有卷的章数之和必须等于 ${targetChapterCount}）
3. **节奏定位**（pacingLevel）：setup / rising / climax / falling / resolution
4. **情感基调**（emotionalTone）：本卷的主导情感
5. **叙事功能**（narrativeFunction）：本卷在全书中承担的叙事功能（50字以内）
6. **核心冲突**：本卷的主要矛盾是什么，谁与谁的冲突（80字以内）
7. **核心悬念**：本卷要抛出或解答的关键悬念是什么（50字以内）
8. **主角成长弧**：主角在本卷中经历了什么内在变化（50字以内）
9. **卷末钩子**：本卷结尾如何吸引读者继续阅读下一卷（50字以内）
10. **关键事件**（coreEvents）：本卷的 3-5 个关键情节节点，每个用一句话概括

请以 JSON 数组格式输出，每个元素的字段如下：
{
  "title": "卷名",
  "chapterCount": 数字,
  "pacingLevel": "setup|rising|climax|falling|resolution",
  "emotionalTone": "情感基调",
  "narrativeFunction": "叙事功能",
  "coreConflict": "核心冲突",
  "coreSuspense": "核心悬念",
  "protagonistArc": "主角成长弧",
  "volumeEndHook": "卷末钩子",
  "coreEvents": ["事件1", "事件2", "事件3"]
}

【Thinking Mode 指令】
在你的思考过程中，请以纯分析模式进行推理：
1. 不要使用角色第一人称内心独白，直接进行逻辑分析
2. 先分析参考结构模式的节奏特点，再思考如何将这些节奏特点映射到《${activeProject.title}》的具体情节上
3. 确保每一卷的核心冲突都源自本小说的角色关系和世界观设定，而非参考作品
```

### 3.3 场景二：自动卷纲生成（无参考文本）

**当前问题**：生成的卷纲内容空泛，只有标题+章数+节奏，缺乏叙事深度。

**根因**：Prompt 只要求了最基本的字段，没有要求核心冲突、悬念、角色弧等深度信息。

**推荐模型**：V4 Pro，Thinking Mode 启用

**推荐参数**：`reasoning_effort: "high"`

**完整 System Prompt**：

```
你是一位资深的长篇小说策划编辑，拥有二十年的网文和实体出版经验。你深谙各类小说流派的叙事节奏——玄幻的升级爽感、悬疑的层层剥茧、言情的情感张力、科幻的概念推演。你为每一部小说设计的分卷架构都像一位建筑师的蓝图：结构严谨、节奏分明、每一卷都有明确的叙事使命和情感走向。
```

**完整 User Message**：

```
请为以下小说设计完整的分卷架构。

【小说信息】
- 书名：《${activeProject.title}》
- 故事梗概：${activeProject.synopsis}
- 主要角色：
${activeProject.characters.map(c => `  · ${c.name}（${c.role}）：${c.description}`).join('\n')}
- 世界观设定：${activeProject.worldBuilding || '未设定'}
- 目标总章数：${targetChapterCount} 章
- 小说类型/流派：${activeProject.genre || '未指定'}

【设计要求】
请设计一个能够承载上述故事的分卷架构。设计时请遵循以下原则：

1. **每一卷必须有独立的叙事使命**：不是简单的时间线切割，而是每一卷都有自己要解决的核心问题
2. **卷间必须有因果递进**：上一卷的结局必须是下一卷的起因，不能是平行的独立故事
3. **主角必须有可见的成长弧**：读者在每一卷结束时都能感受到主角的内在变化

1. **卷名**：体现本卷核心主题的标题
2. **章数分配**：本卷包含多少章（所有卷的章数之和必须等于 ${targetChapterCount}）

4. **情感基调**（emotionalTone）：本卷的主导情感
5. **叙事功能**（narrativeFunction）：本卷在全书中承担的叙事功能（50字以内）
6. **核心冲突**：本卷的主要矛盾是什么，谁与谁的冲突（80字以内）
7. **核心悬念**：本卷要抛出或解答的关键悬念是什么（50字以内）
8. **主角成长弧**：主角在本卷中经历了什么内在变化（50字以内）
9. **卷末钩子**：本卷结尾如何吸引读者继续阅读下一卷（50字以内）
10. **关键事件**（coreEvents）：本卷的 3-5 个关键情节节点，每个用一句话概括

请以 JSON 数组格式输出，字段结构如下：
{
  "title": "卷名",
  "chapterCount": 数字,
  "pacingLevel": "setup|rising|climax|falling|resolution",
  "emotionalTone": "情感基调",
  "narrativeFunction": "叙事功能",
  "coreConflict": "核心冲突",
  "coreSuspense": "核心悬念",
  "protagonistArc": "主角成长弧",
  "volumeEndHook": "卷末钩子",
  "coreEvents": ["事件1", "事件2", "事件3"]
}

【Thinking Mode 指令】
在你的思考过程中，请以纯分析模式进行推理：
1. 不要使用角色第一人称内心独白，直接进行逻辑分析
2. 先根据故事梗概和角色关系，识别出全书的核心矛盾线和主角的终极目标
3. 然后将核心矛盾线拆解为若干阶段性子矛盾，每个子矛盾对应一卷
4. 确保卷间的因果递进关系清晰，每一卷的结局自然引出下一卷的核心问题
5. 最后检查：所有卷的章数之和是否等于 ${targetChapterCount}
```

### 4.2 差异化策略的核心逻辑

**为什么结构化规划用 V4 Pro？**

卷纲和大纲是整部小说的"骨架"，一旦设计不好，后续所有章节都会受影响。V4 Pro 的指令遵循能力（60.0% 胜率 vs Gemini-3.1-Pro）和 CoT 推理能力确保它能准确理解复杂的约束条件（如"所有卷的章数之和必须等于 N"、"每一卷必须有因果递进"），并在思维链中进行深度规划。虽然 Pro 的成本是 Flash 的 12 倍，但卷纲/大纲生成是低频操作（一部小说只生成一次），总成本可控。

**为什么创意写作用 V4 Flash？**

章节正文生成是高频操作（一部小说可能有 100+ 章），成本敏感。V4 Flash 在纯散文评测中得分甚至高于 V4 Pro，且输出量大（4000-5000 词），非常适合长篇正文生成。Flash 的"不听话"问题在正文生成场景中影响较小，因为正文的格式约束远少于结构化输出。

**为什么正文生成禁用 Thinking Mode？**

社区实测表明，Thinking Mode 下的写作"dry and nowhere near as creative"。reasoning_effort=high 会让模型过度分析，削弱创造力。对于需要情感深度和文学性的正文写作，非推理模式反而更好。同时，禁用 Thinking Mode 后 temperature 参数重新生效，可以通过 temperature=0.85 来增加创造力。

**为什么大纲增强用"角色沉浸模式"而非"纯分析模式"？**

大纲增强的目标是增加叙事的"肌理"——场景细节、感官描写、情感微观节拍。这些需要 AI 以"导演"或"读者"的视角去感受故事，而非以"分析师"的视角去拆解结构。角色沉浸模式让 AI 在思维链中以第一人称感受场景，输出更有情感温度。

### 4.3 用户可选的经济模式

考虑到成本敏感的用户，应该提供一个"经济模式"选项，将所有场景都切换到 V4 Flash：

| 场景 | 经济模式配置 | 质量影响 |
|------|------------|---------|
| 卷纲/大纲 | V4 Flash + Thinking 启用 | JSON 格式偶有错误，需要更强的解析容错；指令遵循略差 |
| 章节正文 | V4 Flash + Thinking 禁用 | 无影响（本身就推荐 Flash） |
| 润色 | V4 Flash + Thinking 禁用 | 无影响 |

## 第五章 UI/交互详细设计方案

### 5.1 设计理念

当前 NovelGenius 的交互模式是"全自动批量生成"——用户点击按钮后等待所有大纲一次性生成完毕。这种模式的问题是用户完全被动，无法在过程中介入和调整。

对标 Sudowrite 和 NovelCrafter 的交互设计，我们需要在"全自动"和"全手动"之间找到平衡点——**引导式半自动生成**：AI 负责生成，但在关键节点暂停，让用户确认或调整后再继续。

### 5.2 卷纲编辑器重设计

#### 5.2.1 当前交互流程

```
用户点击"自动生成" → AI 一次性生成所有卷纲 → 用户只能整体接受或拒绝
                或
用户粘贴参考文本 → AI 解析（实际是复制） → 用户只能整体接受或拒绝
```

#### 5.2.2 新交互流程

```
步骤1：用户选择生成方式
  ├── A. 自动生成（AI 根据梗概和角色设计卷纲）
  ├── B. 参考生成（用户粘贴参考文本，AI 借鉴结构但原创内容）
  └── C. 模板生成（用户选择叙事结构模板，AI 填充内容）

步骤2：AI 生成卷纲草案
  → 显示进度条和思维过程摘要（如果使用 Thinking Mode）
  → 生成完毕后以卡片形式展示每一卷

步骤3：逐卷确认与微调
  → 用户可以：
     · 接受某一卷
     · 编辑某一卷的任意字段
     · 要求 AI 重新生成某一卷（保持其他卷不变）
     · 要求 AI 生成同一卷的 2-3 个备选方案供选择
  → 用户确认所有卷后，锁定卷纲，进入章节大纲生成

步骤4：（可选）卷纲一致性检查
  → AI 自动检查所有卷之间的因果递进是否合理
  → 标注潜在的逻辑断裂点
  → 用户确认后最终锁定
```

#### 5.2.3 卷纲卡片组件设计

每一卷以卡片形式展示，卡片包含以下区域：

```
┌─────────────────────────────────────────────────┐
│ 📖 第一卷：[卷名]                    [编辑] [重生成] [备选方案] │
│                                                 │
│ 章数：XX 章  │  节奏：setup  │  情感：希望与迷茫     │
│─────────────────────────────────────────────────│
│ 核心冲突：[80字以内的冲突描述]                      │
│ 核心悬念：[50字以内的悬念描述]                      │
│ 主角成长：[50字以内的成长弧描述]                    │
│ 卷末钩子：[50字以内的钩子描述]                      │
│─────────────────────────────────────────────────│
│ 关键事件：                                        │
│  1. [事件描述]                                    │
│  2. [事件描述]                                    │
│  3. [事件描述]                                    │
│─────────────────────────────────────────────────│
│ ↓ 衔接下一卷：[卷末钩子如何引出下一卷]               │
│                                    [✓ 确认] [✗ 拒绝] │
└─────────────────────────────────────────────────┘
```

#### 5.2.4 "备选方案"功能的数据流

当用户点击某一卷的"备选方案"按钮时：

```
1. 前端发送请求：{
     action: "generate_alternatives",
     volumeIndex: 2,           // 第几卷
     count: 3,                 // 生成几个备选
     lockedVolumes: [0, 1],    // 已锁定的卷（不可改变）
     currentVolume: {...},      // 当前卷的内容（供 AI 参考"不要重复"）
   }

2. Prompt 中注入已锁定卷的信息作为约束：
   "第一卷和第二卷已经确定，内容如下：[...]。
    请为第三卷生成 3 个不同方向的备选方案。
    每个方案必须与已确定的前两卷保持因果递进关系，
    但在核心冲突和关键事件上要有明显差异。"

3. AI 返回 3 个备选方案

4. 前端以标签页形式展示 3 个方案，用户选择一个
```

### 5.3 叙事结构模板库

| 模板名称 | 卷数 | 节奏分布 | 适用类型 |
|---------|------|---------|---------|

#### 5.3.2 模板选择的交互流程

```
步骤1：用户在"生成方式"中选择"模板生成"

  - 模板名称和简介

步骤3：用户选择模板后，AI 根据模板的节奏分布 + 项目信息生成卷纲
```

#### 5.3.3 模板注入 Prompt 的方式

模板信息作为强约束注入到自动卷纲生成的 Prompt 中：

```
用户选择了「英雄之旅」模板，请严格按照以下节奏分布设计卷纲：

- 第三卷「深渊与重生」：占总篇幅 30%，节奏=climax
```

#### 5.4.2 伏笔追踪系统设计

伏笔追踪是 NovelGenius 可以做出差异化的功能。设计如下：

**数据结构**：

```typescript
interface Foreshadowing {
  id: string;
  name: string;              // 伏笔名称（如"神秘玉佩的来历"）
  plantedInChapter: number;  // 埋设章节
  plantedDescription: string; // 埋设时的描述（如"主角在废墟中捡到一枚温热的玉佩"）
  resolvedInChapter?: number; // 揭示章节（可选，未揭示则为 undefined）
  resolvedDescription?: string; // 揭示时的描述
  status: 'planted' | 'hinted' | 'resolved' | 'abandoned'; // 状态
  hints: Array<{             // 中间提示（在揭示前的暗示）
    chapter: number;
    description: string;
  }>;
  importance: 'major' | 'minor'; // 重要程度
}
```

**UI 设计**：在大纲增强阶段，AI 自动识别并标注伏笔的埋设点和建议的揭示点。用户可以在"伏笔追踪面板"中查看所有伏笔的状态：

```

│─────────────────────────────────────────────────│
│ ● 神秘玉佩的来历                                  │

│   状态：[已揭示 ✓]                                │
│                                                 │
│ ● 师父失踪的真相                                  │
│   埋设：第8章 → 暗示：第20章 → 揭示：???           │
│   状态：[待揭示 ⚠] 建议在第30-35章揭示             │
│                                                 │
│ ● 女主角的双重身份                                 │
│   埋设：第15章 → 暗示：无 → 揭示：???              │
│   状态：[缺少暗示 ⚠] 建议在第20-25章增加暗示        │
└─────────────────────────────────────────────────┘
```

**与大纲生成的集成**：在简要大纲推演的 Prompt 中注入伏笔追踪信息：

```
- "师父失踪的真相"（第8章埋设）：本批次暂不揭示，但可以增加一个误导性线索
```

### 6.2 P0 紧急修复的具体改动清单

**改动一：修复 useThinking 死代码**

在 `gemini.ts` 的 `generateAgentResponse` 函数中，`ai.chat.completions.create()` 调用需要增加 `extra_body` 参数：

```
当 useThinking === true 时：
  extra_body: {
    thinking: { type: "enabled" },
    reasoning_effort: "high"
  }

当 useThinking === false 时：
  extra_body: {
    thinking: { type: "disabled" }
  }
```

同时，当 Thinking Mode 启用时，需要从请求中移除 `temperature`、`top_p` 等参数（因为它们会被忽略，移除可以避免混淆）。

**改动二：启用 response_format JSON 模式**

在所有需要 JSON 输出的场景中（卷纲、大纲），将 `response_format: { type: "json_object" }` 传入 API 调用。当前代码中 `responseMimeType: 'application/json'` 只是一个内部标记，没有被传递到 API。

**改动三：消除 Prompt 矛盾**

将 `COMMON_BRAIN_LOGIC` 中的"神经叙事学"概念移除（或改为仅在 Thinking Mode 的思维链中使用），消除与 `ANTI_AI_DETECTION_RULES` 的矛盾。

### 6.3 风险评估

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| V4 Pro 成本过高 | 用户投诉 API 费用 | 提供"经济模式"（全 Flash）选项；在 UI 中显示预估成本 |
| 两阶段法增加延迟 | 卷纲生成时间翻倍 | 阶段一用 Flash（快），阶段二用 Pro；显示进度条和阶段提示 |
| Thinking Mode 输出不稳定 | 偶尔格式错误 | 增加 JSON 解析重试逻辑（最多 3 次）；使用 response_format 强制 JSON |
| 新 Prompt 在不同模型上效果不一致 | 用户使用非 DeepSeek 模型时体验下降 | 在 providerAdapter 中为不同模型维护不同的 Prompt 变体 |
| UI 改动影响现有用户习惯 | 用户不适应新交互 | 保留"一键全自动"选项作为快捷模式；新功能以渐进式方式引入 |

| 现有 Prompt | 简单指令（标题+章数+节奏） | 8 | 3 | 低（无冲突/悬念/角色弧） | 100 |
| 新 Prompt | 编辑人格 + 10 维度约束 | 5 | 10 | 高（含冲突/悬念/角色弧/钩子/事件） | 100 |

现有 Prompt 生成的 8 卷结构虽然覆盖了故事主线，但每卷只有标题、章数和节奏三个字段，缺乏叙事深度。新 Prompt 生成的 5 卷结构不仅卷数更合理（每卷 20 章，信息密度更高），而且每卷都包含核心冲突、核心悬念、主角成长弧、卷末钩子和关键事件列表，为后续的简要大纲推演提供了坚实的锚点。

新 Prompt 的卷间因果递进关系清晰可见：第一卷的卷末钩子"得知家族旧事与王朝武试的关联"直接引出第二卷的王朝武试；第二卷的"被迫进入域外战场"引出第三卷；第三卷的"发现暗影主竟是与家族有关的故人"引出第四卷的宿命主题。这种因果链在现有 Prompt 的输出中完全不存在。

### B.4 章节正文生成对比实验

| 测试组 | Prompt 策略 | 字数 | AI味关键词命中 | 感官描写密度 | 视角稳定性 |
|--------|-----------|------|--------------|------------|----------|
| 现有 WRITER Prompt | 规则化禁止（严禁词列表） | 1713 | 4次（竟然×2, 仿佛×2） | 低（以视觉为主） | 不稳定（全知↔有限切换） |
| 新角色沉浸式 Prompt | 人格化描述（"墨刃"执笔者） | 1671 | 3次（竟然×1, 仿佛×2） | 高（嗅觉+触觉+视觉） | 稳定（始终叶辰有限视角） |

现有 Prompt 的开头是典型的 AI 写作模式："烈日炎炎，炙烤着大地"——环境描写 + 全知视角。新 Prompt 的开头则以感官细节切入："木屑的气味弥漫在空气里，混杂着汗水与泥土的腥气"——嗅觉先行，视角锁定在场景内部。

在内心世界的表达上，现有 Prompt 使用"仿佛那些刺耳的言语与他无关"这样的旁观式描述，而新 Prompt 使用"手掌慢慢收紧，指甲嵌入掌心。疼痛让他保持清醒"这样的具身化表达。后者更符合"展示而非告知"（Show, Don't Tell）的写作原则。

AI 味关键词从 4 次降低到 3 次，降幅有限。这说明仅靠 Prompt 层面的"禁止词列表"或"人格化描述"不足以完全消除 AI 写作痕迹。要进一步降低 AI 味，需要结合以下策略：（1）在 Prompt 中提供 1-2 段目标风格的示范文本（few-shot）；（2）利用 DeepSeek V4 的 Thinking Mode 让模型在思维链中先分析"哪些表达是 AI 味的"，再在输出中刻意回避；（3）后处理阶段用专门的"去 AI 化"Agent 进行二次润色。

### B.5 关键结论

通过四组实测实验，我们得出以下结论：

1. **Prompt 结构比参数调整重要一个数量级**。卷纲复制问题无法通过调整 temperature 解决，只能通过重新设计 Prompt 的任务定位（从"提取"变为"创作"）来解决。这一结论在 DeepSeek V4 Thinking Mode 下尤为重要，因为 Thinking Mode 会忽略 temperature 参数。

2. **信息密度决定下游质量**。自动卷纲生成的字段从 3 个扩展到 10 个后，每一卷都有了明确的叙事使命和因果关系。这些信息将作为后续简要大纲推演的锚点，从源头上解决"章节间缺乏因果链"的问题。

3. **人格化描述优于规则化禁止**。将 WRITER Agent 从"规则列表"改为"人格化角色"后，输出风格有明显改善，但 AI 味的消除仍需多层策略配合。

4. **两阶段法是解决"内容复制"的通用范式**。无论是卷纲参考解析还是其他需要"参考但不复制"的场景，都可以采用"先解构抽象结构→再融合项目上下文重构"的两阶段法。
